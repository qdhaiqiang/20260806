各位好，今天这个汇报，我先把结论放在最前面：我们做了三个真实项目，已经证明 AI 多 Agent 能进入真实的软件工程环节——系统理解、规格形成、实现、测试、Review、交接，这些环节它都能参与。

具体看三个项目：一个是网站快速复刻，一个是穿透式监控平台的复杂后台复刻，还有一个是 renren-security 旧系统的分析治理。

关键证据我先摆几个数字：4 小时完成一个网站、11 小时复刻一个后台、81 张表、757 条风险、19/19 的 E2E 全部通过。

所以我的建议是：选 1 个真实业务模块，启动一个 4 周的受控 Pilot，用真实任务验证效率、质量、安全和团队的采用价值。

接下来我把这四件事展开讲，最后再回到怎么落地。

先说结论：三个项目做下来，我们沉淀出了四项可复用的能力，不是一次性的 Demo。

第一，快速理解系统——页面、代码、数据结构、历史资产，可以并行分析，产出 C4 文档、XRay 分析、既有系统巡检。

第二，把事实转成规格——先形成页面、字段、状态、接口和验收条件，再进入实现，避免上来就瞎写代码。

第三，并行完成工程任务——研究、实现、数据适配、测试、文档，拆开并行跑，19/19 的 E2E 就是这么来的。

第四，用工程治理约束 AI——Build、Test、Review、Merge Gate、人工责任，一个都不能少。

三个项目分别验证了这些能力：机器人项目是快速复刻，穿透平台是复杂业务复刻，renren-security 是遗留系统治理。

记住一句话：这不是单点 Demo 的偶然成功，是一套可复制的软件工程能力模型。下面我讲它要回答什么企业问题。

这一页讲的是：企业真正关心的，从来不是"AI 能不能写代码"，而是"它能不能进入真实工程流程、并且被管理起来"。

技术负责人问的是：输出可不可信、能不能缩短周期、会不会失去架构和代码的控制权、返工会不会变多。

研发负责人问的是：怎么跟现有开发流程融合、能不能沉淀成团队的方法。

信息化负责人最担心安全和合规：源码、模型、数据出不出域，权限和日志怎么管，能不能私有化。

项目管理者关心的是：范围怎么定、进度怎么跟、验收标准和责任边界在哪。

所以我们的回答很明确：不是单点插件，是完整工程闭环；不看代码生成，看可运行、可验证、可交接的结果；不是放弃治理，是用治理约束 AI；不是一次演示，是受控的 Pilot 验证。

所以今天整场汇报，我按"结论前置——项目举证——方法解释——试点建议"这个结构来讲。

接下来进入项目举证。这三个项目不是随便选的，是一条从复刻到接手治理的证据阶梯。

第一个是机器人项目：公开网站 1:1 复刻，验证"快速复刻"的能力。

第二个是穿透式监控平台：复杂后台的复刻，而且是在严格的数据边界约束下做的，验证"复杂业务复刻"。

第三个是 renren-security：旧系统的架构恢复和热点治理分析，验证"遗留系统理解和治理"。

大家看这几个数字，逐级递进：网站项目 2 个 Task、3 个 Agent、4 小时；后台项目 5 个 Task、5 个 Agent、11 小时、81 张表、757 条风险；旧系统项目做的是 677 个热点、churn 78,117 的分析。

三类场景分别证明了快速复刻、复杂业务复刻、遗留系统治理。下面我先把方法论讲清楚，再一个个看证据。

在展开每个项目之前，先说清楚我们的方法论：AI 必须进入完整的工程闭环，不能只停留在"生成一段代码"。

这个闭环有八个步骤：场景选择、系统理解与事实取证、规格形成与验收条件、任务拆解与 Agent 分工、实现与数据适配、Build/Test、人工 Review、交接沉淀。

我强调三个关键原则。

第一，规格先于代码——先有验收条件，再写代码。

第二，AI 的输出必须经过测试和人工责任确认，不能直接进生产。

第三，证据和交付物同步沉淀——代码、测试报告、文档，全部留档。

右边这些就是真实的证据：一段生成的代码，一份页面测试报告，执行时间、工具、通过率都写得很清楚。

一句话：AI 不是绕过工程，而是把工程活动更快、更可见地组织起来。下面用三个项目验证这条链路。

第一个实证：公开网站从巡检到可运行复刻。

项目对象是"青岛市具身智能机器人公共服务平台"。它的范围就是页面巡检、资源本地化、多路由页面复刻、首页和核心交互恢复。

执行事实很简单：2026-07-28，下午 2 点到 6 点，4 小时，2 个 Task、3 个 Agent，Human Touch 1.5 小时，Retry 1 次，DeepSeek 模型成本约 1 元。

交付证据：29 个本地静态资产、15 条发布路由，登录/注册弹窗和卡片交互都能用，并且已经做过现场展示验证。

这个项目说明：对公开站点类需求，AI 平台可以快速跑通"巡检——复刻——验证"的闭环。

但它只是"看得见"这一层，真正考验的是复杂业务。我们看下一个。

第二个实证更关键：在严格的数据边界下，复刻一个复杂的企业管理后台。

穿透式监控平台，界面里有风险详情、状态流转、审核列表、操作审计，业务复杂度明显比网站高一大截。

但重点是边界约束，我们主动给自己上了四把锁：只能登录、只读浏览、界面取证；用既有的 test1.sqlite 结构和数据；禁止建表、迁移、改表；本地 API 只做演示闭环，不等于重建生产后端。

结果：11 小时、5 个 Task、5 个 Agent，Human Touch 4 小时，DeepSeek 成本约 10 元，81 张既有表、757 条风险记录，风险详情、状态流转、审核列表、操作审计全部可见，已远程验证。

这一页想说的是：这个项目的价值不只是"做出页面"，而是在数据边界可控的前提下，完成复杂后台的复刻。

那"像不像"是一回事，能不能跑、可不可信是另一回事——下一页看质量门禁。

很多人会问：AI 生成的页面看着像，但能不能用？这一页就是回答这个问题——AI 生成的结果必须通过工程质量门禁。

三个证据。第一是代码：前后端加 SQL 约 5270 行，前端 6 个 TS/TSX/CSS 文件，后端 5 个 Clojure 文件，定义了 31 条路径、38 个 HTTP 操作。

第二是自动化测试：前端 E2E 19 个用例，19/19 全部通过，npm run build 通过；后端领域测试 2 个测试、12 个断言，0 failure、0 error。

第三是业务闭环：风险信息的列表、搜索、筛选、分页、详情、审核场景都能用，每个页面用例都有独立的 API 返回状态。

我们的验收公式是：AI Generated + Accepted，而 Accepted 等于 Build Pass + Test Evidence + Human Review + 验收标准。

这类证据的意义在于：客户可以把 AI 的输出纳入工程治理，而不是停留在演示层。下面看第三个项目——它不写新功能，专门治理旧系统。

第三个实证换了个方向：renren-security 项目，旧系统分析治理。

这个项目不做功能开发，重点证明一件事：AI 能不能快速恢复对一套旧系统的认知，并输出治理文档。

范围就是：读取既有源码、恢复 C4 四层架构文档、执行 XRay 代码和热点分析、形成后续团队能用的治理建议。

执行事实：2026-08-07 一天，1 个 Task、1 个 Agent，Human Touch 只要 0.5 小时，DeepSeek 成本约 0 元。

产出：多份 C4 架构和模块文档、XRay 窗口内 3 次提交的分析、总 churn 78,117、677 个热点/风险文件，热点目录集中在 renren-ui/src。

要特别说明一句：这个项目没有新增需求，汇报材料停留在分析和文档交付层，不宣称完成了功能修改。

它证明的是：面对遗留系统，AI 能先把"看不懂、接不住"的问题，转成可治理的文档和风险视图。三个项目讲完了，下一页我把它们串成一条链路。

三个项目讲完，现在把它们串成一条链路——这就是跨项目验证出来的 AI 软件工程能力模型。

七个环节：系统理解、事实取证、规格形成、任务拆解、实现与数据适配、测试与 Review、交付沉淀。

三个项目各证明一段：机器人项目证明快速理解和页面复刻；穿透平台证明复杂业务约束下的实现和验证；renren-security 证明遗留系统理解、C4 架构恢复和风险洞察。

把这七个环节合起来，就是一条可复制的软件工程生产链——从理解到沉淀，形成可复用知识；从实现到适配，保证可维护；从自动化到人工，双重把关；从事实到报告，支撑可信交付。

所以结论不是"三个孤立 Demo"，而是不同场景、同一链路，验证了一套能力闭环。

那这条链路具体靠什么跑起来？下一页讲多 Agent 的组织方式。

这条链路的核心，不是开很多个聊天窗口，而是把任务变成一条可管理的工程生产线。

一个业务任务进来，先到一个 Planner / Orchestrator，它负责理解任务、拆解计划、分配到 Agent、跟踪进度和依赖。然后 Research、Coding、Test、Review 几个 Agent 各司其职，最后产出 Evidence / Report。

为什么比单一对话有效？三个原因：多任务隔离，每个 Agent 专注单一目标，减少上下文污染；上下文分层，按角色维护最小必要上下文，省 Token、更稳定；并行执行，研究、实现、测试并行推进，缩短端到端时间。

但人工控制点一个都不能少：任务定义、规格确认、Merge Gate、验收责任——做什么、做到什么程度、合不合并、验不验收，还是人来定。

一句话：多 Agent 的价值是把复杂工程活动组织起来，不是替代工程治理。那效率到底从哪来？下一页看数据。

这一页回答"效率从哪来"。提效不是来自一句提示词，而是来自工程组织方式的变化。

有五个机制：并行化，多线任务同时跑；上下文外显，文档、代码结构、风险信息结构化沉淀；任务隔离，把复杂工作拆成独立模块；自动化验证，用测试和静态分析快速验证；人工聚焦，把人的时间放到决策、例外处理和风险评估上。

看右边的对比表：网站项目 4 小时、后台 11 小时、旧系统一天；Human Touch 分别是 1.5 小时、4 小时、0.5 小时；成本约 1 元、10 元、0 元。

当前已经证明的是：AI 能显著缩短系统理解、后台复刻和验证准备的时间。

但我要说实话：最终的效率收益，还要在客户自己的真实项目里，跟基线做对比才能下结论。所以下一步必须讲治理，没有治理，效率再高也不敢用。

这一页是能不能进企业级流程的底线：质量、安全、责任，三条边界必须保留。

质量治理：Build Pass、Test Evidence、Human Review、Acceptance Criteria、Merge Gate，一个不能少。

安全边界：Repo 留在客户侧，源码、模型、数据的边界清晰，权限控制和日志留痕，支持私有化和受控接入。

责任边界：需求责任、合并审批、最终验收，都归人。

右边这张图就是完整的落地方案：客户侧仓库、AI 代理运行时、模型、构建测试、证据存储、人工评审、合并，全在一条可控的链路上。

核心就一句话：AI 可以进入企业工程，但必须在可控边界内运行。

边界讲清楚了，下一步就是：怎么判断这件事到底值不值得规模化？

怎么判断值不值得规模化？我们不看代码行数，看工程结果和采用质量，一共六类指标。

Flow 效率：Lead Time、Cycle Time、Throughput。

AI 自治度：独立完成率、人工介入率、Retry 次数。

Quality 质量：First-pass Acceptance、缺陷率、测试通过率。

Human Touch：人工耗时、Review 耗时、交付触达时间。

Governance 治理：日志留痕、合规性、可追溯性。

Economics 经济性：模型成本、单任务成本、成果产出比。

落地工具是建立一张 AI Task Evidence Ledger——每个任务记 TaskID、Agent、起止时间、Human Touch、Test、Review、Acceptance、Cost。

只有形成任务级的证据账本，才能把试点结果变成可复核的管理结论。下一页讲具体的采用路径。

最后一页，落到行动。我的建议是：先从单点验证，再到规模化复制，五步走。

第一步场景筛选，从业务价值高、风险可控的模块里选试点；第二步基线建立，梳理现状、建立基线和验收标准；第三步受控验证，在受控环境里跑，确保安全和质量；第四步复盘评估，看效果和投入产出；第五步复制推广，把沉淀下来的资产和最佳实践复制到更多团队。

优先建议切入的，是旧系统维护小需求、后台审批/报表模块、界面复刻与测试补齐、文档恢复与系统理解这些风险可控的场景。

不建议第一批碰的，是核心交易主链路、高耦合大规模重构、安全边界不清晰、需求长期频繁变动又没有基线的场景。

总的原则就一句：先验证能不能稳定进入工程流程，再验证值不值得规模化复制。

我的汇报就到这里。核心结论是：能力已经验证，下一步是启动一个 4 周的受控 Pilot，用真实任务说话。谢谢大家，欢迎提问。
